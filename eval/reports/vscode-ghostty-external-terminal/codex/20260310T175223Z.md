        ## Control vs Human PR
        ### Key differences
        - PR launches Ghostty on macOS via /usr/bin/open -na Ghostty.app --args; B spawns the ghostty binary directly, bypassing the standard macOS app-launch mechanism
- PR uses Ghostty-native CLI flags (--working-directory, --wait-after-command, -e); B wraps commands in bash (-e bash -c bashCommand) like the old Linux terminal pattern
- B adds a new public method runInTerminalWithSpawner to both Mac and Linux service classes, changing the public API surface; PR does not modify public APIs
- B adds getDefaultTerminalOsx() that auto-detects Ghostty from TERM_PROGRAM; PR does not add auto-detection and uses the existing DEFAULT_TERMINAL_OSX constant
- PR refactors error handling into setupSpawnErrorHandling() and Linux spawn into spawnTerminalWithEnv(); B adds getSanitizedEnvironmentWithOverrides() and getBashCommand() instead—different refactoring choices
- B adds 2 new constants (GHOSTTY_TERMINAL_OSX, GHOSTTY_TERMINAL_LINUX) to common module; PR adds none
- B mutates process.env.TERM_PROGRAM in tests (with teardown); PR tests don't require environment mutation

        ### Strengths
        - No critical bugs—process lifecycle is handled correctly throughout
- More comprehensive test coverage with 6 new tests covering multiple code paths (spawn, run, detection) on both platforms
- Clean helper extraction: getSanitizedEnvironmentWithOverrides() and getBashCommand() reduce duplication
- runInTerminalWithSpawner enables proper dependency injection for testing without accessing private methods

        ### Risks
        - Spawns ghostty binary directly on macOS instead of using /usr/bin/open, which may not correctly launch the .app bundle or handle Gatekeeper/sandboxing
- Changes public API by adding runInTerminalWithSpawner—callers and interface consumers may need updating
- Prioritizes Ghostty detection above Debian default in getDefaultTerminalLinux, which could change behavior for Debian+Ghostty users unexpectedly
